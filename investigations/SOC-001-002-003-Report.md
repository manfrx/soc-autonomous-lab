## 1. Executive Summary

Three attack simulations were executed against the SOC lab Windows 11 endpoint to validate the
Wazuh detection pipeline end-to-end. **All three scenarios were successfully detected and
triaged within the Wazuh manager**, at alert severities ranging from level 3 to level 12.

| ID | Scenario | Simulated action | Detected | Highest severity | Primary Wazuh rule |
|---|---|---|---|---|---|
| **SOC-001** | Brute force / password guessing | Local account `soc-test-user` created; repeated SMB network logons with a wrong password | ✅ Yes | **Level 8** | `60122` (Logon Failure), `60110` (User account changed) |
| **SOC-002** | Suspicious PowerShell | Base64-encoded (`-EncodedCommand`) PowerShell spawning a hidden `cmd.exe` + web request | ✅ Yes | **Level 12** | `92057` (base64 encoded command), `91809` (Base64 decoding method) |
| **SOC-003** | Unauthorised file modification | `C:\SOC-Lab\important.txt` overwritten (`echo hacked >`) | ✅ Yes | **Level 7** | `550` (Integrity checksum changed — realtime FIM) |

The exercise exercised **three independent detection surfaces** — Windows Security audit log,
Windows PowerShell Operational log (script-block logging) and Sysmon — proving the agent's
collection profile is correctly scoped and that the manager's ruleset decodes each source.

**Key finding (positive):** the full chain works — endpoint event → agent → SSH port-forward →
Wazuh manager (`remoted`) → ruleset match → alert. Correlation across SOC-001/002/003 was
successful within a single 3-minute window.

**Key finding (negative / risk):** the exercise required **four prior remediation actions** before
any of this could work. The endpoint was previously invisible to the manager. See §7
*Detection Gaps Identified & Remediated*. The environment was not initially capable of detecting
these scenarios, and the agent was running a version the manager could not accept.

## 6. Recommendations for Containment

### 6.1 Immediate (endpoint — `DESKTOP-0U2NKV7`)

1. **Disable and delete the test account** `soc-test-user` (SID `…-1003`). It was created purely for
   SOC-001 and must not persist:
   ```powershell
   Disable-LocalUser -Name 'soc-test-user'
   Remove-LocalUser -Name 'soc-test-user'
   ```
   If it is retained for re-testing, set a random 32+ character password and add it to a
   `Disabled` state with no interactive logon rights.
2. **Remove the test artefact** `C:\SOC-Lab\important.txt` (SHA256
   `12bd990b6a486df44720e5de8fe702469d614ee91fe9bf857ba59f3821de829b`) and the `C:\SOC-Lab`
   directory, unless the directory is intentionally retained as a FIM canary.
3. **Confirm no persistence from SOC-002.** The hidden `cmd.exe /c whoami /url` child terminated
   normally (exit 0, stdout `stage1-complete`), and no `Invoke-WebRequest` session persisted
   (connection to `127.0.0.1:9` was refused). Verify nonetheless:
   ```powershell
   Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" | Select ProcessId,CommandLine
   Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup"
   Get-ScheduledTask | Where-Object {$_.State -ne 'Disabled'}
   ```
4. **Apply an execution-policy lockdown** to block inline `IEX` of decoded content:
   `Set-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell' ConstrainedLanguage -Value 1` — or,
   preferably, deploy WDAC/AppLocker blocking `-EncodedCommand` from non-admin contexts.

### 6.2 Short term (detection engineering)

5. **Add a correlation rule for brute force.** Wazuh's stock ruleset alerts on each individual 4625
   but does **not** correlate volume. Add a frequency rule so repeated failures escalate:
   ```xml
   <rule id="100100" level="10" frequency="5" timeframe="120">
     <if_matched_sid>60122</if_matched_sid>
     <description>Multiple failed logons for the same account within 120 seconds - possible password guessing</description>
     <mitre><id>T1110.001</id></mitre>
   </rule>
   ```
   The 4 confirmed events in this exercise span `02:01:22`–`02:03:31` (129 s) for the same account —
   precisely the pattern such a rule targets.
6. **Enable the account-lockout policy** on Windows endpoints (`LockoutThreshold=5`,
   `LockoutDuration=30`, `ResetAfter=30`) so brute force is self-limiting and generates a
   `4740` account-locked event for correlation.
7. **Add `Microsoft-Windows-PowerShell/Operational` and `Microsoft-Windows-Sysmon/Operational` to
   the agent baseline.** These were **not** present by default and are required for SOC-002-style
   detection. Codify them in the agent `ossec.conf` template so they are not lost on redeploy.
8. **Add `C:\SOC-Lab` to a managed FIM watch list** (or, in production, watch
   `%ProgramData%`, `%AppData%`, startup folders and script directories) with `realtime="yes"` and
   `check_all="yes"`.

### 6.3 Medium term (platform / infrastructure)

9. **Remove the Bastion from the agent data path.** The agent's visibility currently depends on an
   SSH tunnel with a **1-hour session TTL** — when the session expires, the endpoint silently goes
   dark (this happened twice during this engagement). Deploy a persistent TCP proxy on the manager
   (e.g. `socat`/nginx-stream) and point the agent's `<server><address>` at the manager's stable
   private IP, so agent connectivity is independent of interactive sessions.
10. **Automate the session renewal** with a scheduled task that recreates sessions and tunnels on a
    rolling basis, or raise `max-session-ttl-in-seconds` where the bastion's public CIDR allow-list
    can be tightened accordingly.
11. **Codify the OCI network changes in Terraform.** The NSG and both security lists are tagged
    `ManagedBy: terraform`; the 1514/1515 rules added during this engagement were applied via the
    CLI and **will be reverted by the next `terraform apply`** unless added to the `.tf` files.
12. **Raise the manager version.** The manager is Wazuh 4.9.2 (EOL). The endpoint agent had to be
    **downgraded** from 4.13.0-rc5 to 4.9.2 because Wazuh rejects `agent_version > manager_version`
    (`ERROR: Agent version must be lower or equal to manager version`). Plan an upgrade of
    manager → indexer → dashboard → agent so new agent releases can be adopted.
13. **Tune out low-fidelity Sysmon rules.** `92029` (8 alerts) and `92213` (11 alerts) fired
    exclusively on analyst tooling in this window. Baseline-tune them (e.g. exclude the
    `__PSScriptPolicyTest_*.ps1` pattern and known tooling paths) to protect analyst signal.

## 7. Detection Gaps Identified & Remediated (pre-requisites)

The endpoint was **not detectable** when this phase began. Five blocking issues were found and fixed:

| # | Gap | Impact | Remediation |
|---|---|---|---|
| 1 | **NSG** on the instance VNIC allowed 1514/1515 only from `10.30.2.0/24` (its own subnet), not from the bastion `10.30.1.0/24` | Zero packets reached the host on 1514/1515 — the agent could never connect | Added INGRESS rules TCP 1514/1515 from `10.30.1.0/24` (`oci network nsg rules add`) |
| 2 | **Security lists** — instance subnet SL had no 1514/1515 ingress; bastion subnet SL had no 1514/1515 egress | Same block at the VCN layer, above iptables | Added ingress (from `10.30.1.0/24`) and egress (to `10.30.2.0/24`) for 1514/1515 |
| 3 | **Host iptables** on the manager REJECTed everything except 22 | Bastion traffic to 1514/1515 was dropped even once the OCI layer allowed it | Added ACCEPT rules for 443/1514/1515 from `10.30.1.253/32`; persisted with `netfilter-persistent save` |
| 4 | **Agent version** 4.13.0-rc5 vs manager 4.9.2 | Manager rejected the agent: `Agent version must be lower or equal to manager version` | Clean uninstall + install of agent **4.9.2**, preserving `client.keys` (agent kept ID `001`) |
| 5 | **Agent collection profile** missing the PowerShell channel and `C:\SOC-Lab` FIM scope | SOC-002 and SOC-003 would have been invisible | Added `Microsoft-Windows-PowerShell/Operational` localfile, enabled ScriptBlockLogging (policy `= 1`), added `<directories realtime="yes" check_all="yes">C:\SOC-Lab</directories>` |

**Verified end state:** `ID: 001, Name: windows-endpoint, IP: any, Status: Active` on the manager,
`WazuhSvc` Running/Automatic, agent log showing `(4102): Connected to the server ([127.0.0.1]:1514/tcp)`,
and live alert ingestion demonstrated by this report.

### 8.3 Reproducibility notes

Three execution defects were found and corrected during the exercise, recorded here so the
detection test can be re-run reliably:

1. `net use` requires `/user:<name>` as a **single** argument with the password positional
   (`net use \\host\share <password> /user:<name>`). Splitting `/user:` and the username produced
   a syntax error and **zero** logon attempts.
2. `Invoke-Expression` cannot bind a `System.Byte[]`; the decoded payload must be cast with
   `[Text.Encoding]::Unicode.GetString(...)`.
3. `Get-WinEvent -FilterHashtable` `StartTime` is interpreted in **local** time — passing a UTC
   value returns zero events and produces false-negative counters. Manager-side alert queries were
   used as the authoritative verification instead.
